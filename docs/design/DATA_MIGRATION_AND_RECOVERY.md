# 游戏化升级的数据迁移与回退

## 现有资料如何保留

本次沿用原有 User、Course、KnowledgeNode、Task、Note 的主标识。新增 MaterialVersion、SourceSpan、ExpeditionProgress、QuestRun、ExpeditionOperation、RewardGrant、ExpeditionAccount 七类表，不把原任务或手动掌握度改写为知识证据。迁移 SQL 只有新增表、索引和关联约束，没有清空旧表或批量调整用户余额。

用户首次进入远征时，在事务中读取原 User 余额，把等级、经验、结晶和历史能量保存到 ExpeditionAccount.legacySnapshot。User 仍是唯一钱包。快照不是第二份可领取余额，不与本机数据相加；新奖励通过唯一账本记录后修改 User。旧签到、计时与完成按钮停止发放奖励，但到访和投入记录仍保留。

| 来源 | 迁移和归属规则 | 回退依据 |
| --- | --- | --- |
| 当前云端账号 | 继续使用相同 User.id 和课程等 ID；首次启用保存余额快照 | 原表、不可变操作账本、发布前数据库分支 |
| Android 已标识账号的旧 DataStore | AccountStores 只有在目标空间为空且旧 user_id 与当前账号一致时才复制；不修改来源文件 | OwnedLegacyMigration.cleanUp 不删除原文件 |
| Android 未标识归属的旧本机资料 | 保留原田园入口用于只读核对或导出，不能自动上传到任意新账号 | 原文件和原有本机入口 |
| 游客 | RAM 中独立会话，不导入账号、不参加云迁移；主动导出由用户保管 | 没有自动备份，结束即清空 |
| 新版账号离线草稿 | Web 按已验证账号与 Token 摘要隔离；Android 按 API 地址和账号隔离 | 本机草稿、原版本、原设备 epoch；冲突不覆盖 |

这里没有实现“任意旧 Android 数据库一键并入任意云账号”。缺少来源和所有权证据时保留数据，不能声称已经完成迁移。不同版本、设备或安装签名之间的实际迁移仍需要在持有原始数据的设备上验证。

## 升级前核对

本地 SQLite 使用现有一致性备份脚本，不能复制仍在写入的单个数据库文件冒充完整备份。先保留备份，再执行 `node scripts/upgrade-local.cjs`，不要对已有库重跑初始化 SQL。生产 PostgreSQL 使用 `npm run cloud:migrate`，从受忽略的环境配置读取直接连接，不把凭据复制到报告。

迁移前保留来源环境、数据库分支或备份标识、源码版本和迁移文件摘要。临时分支先应用同一迁移并运行真实事务测试；正式环境只应用已核验的新增迁移。新版运行前两端使用同一后端，不能将本地测试库当成正式共享数据。

## 出现问题时

优先保留失败请求的 opId、当前服务端版本及客户端原答案。重试相同操作返回原确认结果；同一操作编号换内容会冲突。资料更新使仍引用旧版本的未完成远征失效，已保存证据继续指向原资料。删除课程保留奖励去重账本，避免复制课程重新领首次奖励。

如需回退服务，先停止写入并保留当前数据库副本，再切换已知可运行的部署。新增表可以暂留，不能为回到旧界面直接删除学习证据。3.2.5 使用旧经济规则；回退后应暂停新奖励活动，不能让两套结算并行。正式恢复应核对快照、原余额和账本差额，由运维在明确备份点或修复版本上恢复，禁止把两份余额直接求和。

## 已有验证与尚缺证据

已进行临时 SQLite 迁移及事务测试，并在独立 Neon PostgreSQL 分支验证真实迁移、重复提交、并发奖励、设备接管、线下自述去重、原子消费和 token 不入账本。临时分支的验证不等同于正式库已迁移。未持有带旧数据的 Android 真机，因此没有声称完成真机恢复或跨签名安装迁移。
